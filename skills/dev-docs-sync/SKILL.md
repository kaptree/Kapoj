# kapOJ 开发文档同步

每次完成开发后，文档要反映代码的当前状态。这个 skill 的目标是：让下一个人（或下一次对话）只读文档，就能知道功能现在做到哪、接口怎么调、表结构是什么、还差什么。

## 相关文档

- `DEVELOPMENT.md`：详细开发规格，包含架构、数据库设计（第 3 节）、各功能模块的需求与关键接口（第 4、5、6、7 节）、里程碑（第 9 节）。
- `plan.md`：最初的功能清单，是 `DEVELOPMENT.md` 的来源。
- `docs/开发日志.md`：按时间记录每次开发的变更。如果不存在就创建。

## 步骤

### 1. 确定本次变更范围

先弄清楚改了什么，不要凭记忆写。依次检查：

- 如果项目是 git 仓库，用 `git status` 和 `git diff` 查看改动。
- 如果不是 git 仓库，用 `find . -newer <某个参照文件> -type f`（排除 `node_modules`、`.git`）找出近期修改的文件，并结合本次对话中做过的事情确认。
- 把改动归类为：接口、数据表/模型、功能逻辑、前端页面、配置/部署、测试。

### 2. 找到对应的文档章节

| 改动类型 | 需要更新的位置 |
|---------|--------------|
| 新增或修改接口 | `DEVELOPMENT.md` 对应模块的「关键接口」表（第 4、5、6 节） |
| 数据表或字段变化 | `DEVELOPMENT.md` 第 3 节对应的 SQL 片段 |
| 功能行为变化 | 对应模块的「功能需求」或「关键设计」（第 4–7 节） |
| 模块完成或进度变化 | `DEVELOPMENT.md` 第 9 节里程碑表；`plan.md` 中对应条目 |
| 配置、环境变量、启动方式 | 项目 README（如有）；`DEVELOPMENT.md` 第 2 节 |

### 3. 更新原则

- **写当前的实际行为，不要只抄原始规格。** 如果实现与规格有出入（字段名、接口路径、判定规则、阈值、积分等），以代码为准，并在对应位置加一行「实现差异」，写明原因。不要悄悄改掉原规格的设计意图。
- **不修改第 8 节的 Codex 提示词。** 这些是当时交给 Codex 的原始任务描述，属于历史记录。如果实现偏离了提示词，在该模块的功能需求下方写「实现差异」说明即可。
- **不新增没有实现的功能。** 计划中但未做的内容保留原样，并标注「未实现」。
- **只改需要改的部分。** 不重排整个文档，不改无关章节的措辞和格式，保持原有的中文表述风格。
- **接口和字段名必须与代码一致。** 写之前在代码里搜索路径或字段名确认，不要靠猜。

### 4. 写开发日志

在 `docs/开发日志.md` 末尾追加一条，格式如下：

```markdown
## YYYY-MM-DD：<模块名> <简要描述>

- **变更内容**：用 1–3 句话说明做了什么
- **涉及模块**：如 用户与认证、代码测评沙盒
- **涉及文件**：关键文件路径
- **文档更新**：列出本次改了 `DEVELOPMENT.md` 的哪些章节
- **实现差异**：与规格不一致的地方及原因（没有则写「无」）
- **待办**：尚未完成的部分（没有则写「无」）
```

日志只记录事实，不写评价或计划性的话。

### 5. 更新里程碑状态

在 `DEVELOPMENT.md` 第 9 节的里程碑表中标注进度。使用统一的标记：

- ✅ 已完成
- 🚧 进行中
- ⬜ 未开始

只有当模块的验收标准（对应 Codex 提示词末尾的「验收标准」）确实满足时，才标记 ✅。没有通过验收的，标记 🚧。

### 6. 核对

在结束前逐项确认：

- 文档中提到的接口路径、字段名、枚举值，都能在代码里搜到。
- 修改后的 Markdown 表格列数一致，没有断行或破坏格式。
- 「目录」中的锚点链接仍然有效（如果新增或改名了章节）。
- 没有删除未改动的内容。

可以用 `git diff -- DEVELOPMENT.md plan.md docs/开发日志.md` 检查本次改动，确保只包含预期的修改。

### 7. 向用户汇报

用简短的中文列出：

- 改了哪些文档、哪些章节
- 发现的实现差异（如有）
- 里程碑状态有没有变化
- 任何不确定、需要用户确认的地方

## 注意事项

- 如果本次改动很小（例如只修了一个 bug 而接口和行为都没变），只需写开发日志，不需要改规格文档。
- 如果无法确定某个改动该归到哪个模块，先问用户，不要猜。
