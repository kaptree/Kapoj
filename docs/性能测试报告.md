# kapOJ 性能与部署配置测试报告

> 测试日期：2026-11-12
> 测试对象：当前仓库 HEAD（Go 后端 + Vue 前端 + PostgreSQL 17 + Redis 7 + 独立 Docker 评测服务）
> 测试环境：macOS + Docker Desktop（8 vCPU / 8 GB 虚拟机），用容器 CPU/内存限额模拟 4 核 4 GB 服务器
> 测试数据：10,200 用户、2,001 道题、100,000 条提交（数据库 157 MB）、200 个可登录账号、1 场 100 人比赛

## 1. 结论

**你的 4 核 4 GB、8 Mbps、30 GB、Ubuntu 20.04 服务器可以跑起来，适合小型 OJ（几十到一两百活跃用户、以刷题和少量比赛为主），但有三个前提：**

1. **评测服务并发设为 1**：`KAPOJ_JUDGE_CONCURRENCY=1`。4 GB 下默认并发 2 有 OOM 风险（每次编译容器上限 1 GB）。
2. **配置 Docker 日志轮转**：后端每个请求写一行日志，高流量下日志是 30 GB 磁盘最大的隐性消耗。
3. **控制测试数据体积**：系统镜像 + 数据库等基础占用约 7–10 GB，剩余约 18–21 GB 给题目测试数据、头像、证书和备份。

如果要做 **100 人以上、提交量较大的比赛**，建议内存升到 **8 GB**（评测并发 2），或把评测服务放到独立机器。

### 关键数字速览

| 指标 | 实测结果 |
|---|---|
| 空闲内存（应用容器） | 约 270 MB；加系统/Docker 约 0.8 GB |
| 空闲 CPU | < 1% |
| 典型浏览压测（50 并发请求） | 约 410 RPS，P95 214 ms，CPU 约 3.1 核 |
| 登录 | 约 29 次/秒（2 核时），CPU 跑满 |
| 客观题提交 | 约 120 次/秒，PostgreSQL 约 1.5 核 |
| 榜单接口（100 人） | 约 357 RPS，P95 97 ms，响应约 39.7 KB |
| C++ 评测（10 个测试点） | 单份约 10 秒；并发 1 约 7 份/分钟，并发 2 约 12 份/分钟 |
| 数据库增长 | 约 1.4 KB/提交；10 万提交 157 MB；100 万约 1.5 GB |
| 初始页面传输 | 首页约 164 KB、题目详情约 268 KB、提交页约 283 KB（gzip） |
| Docker 镜像 | 约 3.87 GB（gcc、Go、Java、Python、PostgreSQL、Redis、server、judge） |

## 2. 测试方法

- 用独立数据库 `kapoj`、独立 Redis、独立存储目录和独立端口启动一套 perf 栈，未触碰原有开发库和开发服务。
- 容器限额模拟 4 核 4 GB：
  - 后端：1.5 CPU / 512 MB
  - PostgreSQL：2.25 CPU / 1 GB
  - Redis：0.25 CPU / 256 MB
  - judge：1 CPU / 512 MB（沙盒容器另算，每次编译上限 1 GB）
  - Nginx：0.25 CPU / 64 MB
- 压测工具为自写的 Go HTTP 压测器，统计 RPS、平均/P50/P95/P99/最大延迟、响应字节数、HTTP 状态。
- 数据库用 SQL 造真实规模数据：2,001 题（题面约 1.5 KB）、10,000 个普通用户、100,000 条提交（代码约 800 B + 10 个测试点的 judgeResult）。
- 评测测试使用一道 10 个测试点的 A+B 题，C++ 提交，统计从 POST 到终态的时间。
- 编译内存用容器 cgroup `memory.peak` 读取，和 judge 的实际容器参数一致（`--memory 1g --cpus 1`）。

**注意：** 这是 Docker Desktop 上的 Linux 容器实测，不是在你的 Ubuntu 服务器上直接实测。真实 Linux 服务器的容器启动通常比 Docker Desktop 快，评测吞吐会更好；API 吞吐主要受 CPU/数据库影响，量级接近。绝对数字建议上线前在目标服务器复测一次。

## 3. 空闲资源占用

| 组件 | 内存（docker stats） | 实际匿名内存/说明 | 空闲 CPU |
|---|---:|---|---:|
| Go 后端 server | 44 MB | 约 44 MB | 0.06% |
| PostgreSQL 17 | 185–245 MB | 共享缓冲 128 MB + 后端进程；文件页缓存可回收 | 0.17% |
| Redis 7 | 13 MB | 约 10 MB | 0.69% |
| judge | 9 MB | 约 5 MB | 0.08% |
| Nginx（前端静态） | 19 MB | 约 6 MB | 0% |
| **合计** | **约 270 MB** | 加系统/Docker 约 **0.8 GB** | **< 1%** |

PostgreSQL 的 `docker stats` 会包含页缓存，看起来有几百 MB，但大部分是可回收的文件缓存。真正不可回收的部分约 180 MB（128 MB shared_buffers + 连接/系统开销）。内存不是空闲时的瓶颈。

## 4. 压测结果

### 4.1 浏览类接口（题目列表/详情/榜单/我的信息）

混合比例：题目列表 40%、题目详情 30%、Rating 榜 15%、`/users/me` 15%。全部带登录态。

| 并发请求 | RPS | 平均延迟 | P95 | 最大 | 错误 | 非 2xx |
|---:|---:|---:|---:|---:|---:|---:|
| 10 | 326 | 30 ms | 83 ms | 211 ms | 0 | 0 |
| 50（4 核均衡限额） | **411** | 121 ms | **214 ms** | 403 ms | 0 | 0 |
| 100（4 核均衡限额） | 388 | 256 ms | 491 ms | 897 ms | 0 | 36（500） |

- 50 并发时 CPU：后端约 0.8 核、PostgreSQL 约 2.3 核、Redis < 0.1 核，合计约 **3.1 核（4 核的 78%）**。
- 100 并发时出现 36 个 500，原因是 PostgreSQL `max_connections=100` 被耗尽：`FATAL: sorry, too many clients already`。后端没有设置 GORM 连接池上限，突发并发会一直开连接。
- 每个带登录态的题目请求会实时解析 RBAC 权限（用户、角色、权限共 3 条 SQL），这是浏览类 CPU 的主要来源。好处是权限变更立即生效；代价是高并发下数据库压力较大。

### 4.2 提交记录列表

这是对数据量最敏感的接口。列表查询会 `JOIN users/problems/contests` 并做 `COUNT(*)`。

| 数据量 | 并发 | RPS | 平均延迟 | P95 | 说明 |
|---|---:|---:|---:|---:|---|
| 1 万条提交 | 10 | **104** | 95 ms | 192 ms | 小型部署可用 |
| 10 万条提交 | 10 | **14** | 697 ms | 1072 ms | 明显变慢，PG 跑满 |

10 万条时单次 `COUNT(*)` 冷/热执行约 67 ms，10 个并发就能把 1.5 核 PostgreSQL 跑满。该组测试时 PostgreSQL 限额为 1.5 核；4 核均衡分配会略高，但它仍是数据量增长后的主要瓶颈。建议在提交量接近 5 万前优化这个查询（缓存总数、拆掉不必要的 JOIN、或单独维护计数），否则“测评记录”页会成为瓶颈。

### 4.3 登录

| 并发 | RPS | 平均延迟 | P95 | CPU |
|---:|---:|---:|---:|---:|
| 10 | 29 | 337 ms | 494 ms | 2 核跑满（bcrypt） |

29 次/秒意味着 200 人同时登录约 7 秒完成，1000 人约 34 秒（4 核会更快）。登录风暴是瞬时 CPU 峰值，不是常态。

### 4.4 客观题提交（写入路径）

使用客观题（不进入 judge），200 个账号轮换，每用户 1 秒冷却：

| 指标 | 结果 |
|---|---:|
| 成功提交 | 约 **120 次/秒** |
| 服务端 CPU | 0.6 核 |
| PostgreSQL CPU | 1.5 核（跑满） |
| 尝试中被限流（429） | 约 60%（符合每用户 1 秒冷却） |

代码题提交还会多一步入队和评测，写入路径本身不是瓶颈。

### 4.5 比赛榜单

100 名参赛者、300 条比赛提交：

| 指标 | 结果 |
|---|---:|
| 响应大小 | **39.7 KB** |
| 单次耗时 | 约 7 ms |
| 20 并发 RPS | 357 |
| P95 | 97 ms |
| 20 并发 CPU | 后端约 1.0 核 + PG 约 2.1 核 |

前端比赛详情页每 **30 秒**自动刷新一次榜单。100 人在线时约 3.3 RPS × 39.7 KB ≈ **1.1 Mbps**，8 Mbps 足够；500 人在线约 5.3 Mbps，仍然可用。只有用户频繁手动刷新或参赛人数更多时才需要担心带宽。

## 5. 评测服务（judge）

### 5.1 单份提交耗时

C++、10 个测试点、每题 1000 ms / 256 MB：

| 场景 | 结果 |
|---|---:|
| 单份提交从入库到终态 | **约 10.2 秒** |
| 并发 1：6 份总耗时 | 51.3 秒（约 **7 份/分钟**） |
| 并发 2：8 份总耗时 | 41.5 秒（约 **12 份/分钟**） |
| judge 进程 CPU/内存 | 峰值 0.26 核 / 12 MB |
| 每个沙盒容器 | 1 CPU；运行内存按题目限制（本测试 256 MB） |

judge 每个测试点启动一个容器，10 个测试点就是 1 次编译 + 10 次运行容器。Docker Desktop 上容器启动偏慢，真实 Linux 通常会快一些，但“每测试点一个容器”的结构决定了它仍然是主要延迟来源。

### 5.2 编译峰值内存（容器上限 1 GB）

| 语言 | 编译耗时 | 峰值内存 |
|---|---:|---:|
| C | 0.20 s | 33 MB |
| C++ | 1.02 s | 200 MB |
| Java | 0.63 s | 114 MB |
| Python3 | 0.23 s | 13 MB |
| Go | 7.59 s | **315 MB** |

实际峰值远低于 1 GB 上限，但上限仍是 1 GB。**4 GB 服务器上并发 2 时，两份编译理论上可占 2 GB**，加上后端/PostgreSQL/Redis/系统约 1.5–2 GB，最坏情况会触顶。正常代码实测约 0.6 GB（两份 Java/C++），但 Go 或恶意代码会更接近上限。

### 5.3 对 4C4G 的建议

- **`KAPOJ_JUDGE_CONCURRENCY=1`**：安全，评测时仍留约 3 核给 API。
- 如果一定要并发 2，建议 8 GB 内存，或把编译内存上限从 1 GB 降到 512 MB（需要改 judge 代码/配置，当前未开放环境变量）。
- 比赛结束后的集中评测是最容易出现“评测排队 + API 变慢”的时段；4 GB 下不要把并发开到 4。

## 6. 存储增长速度

### 6.1 数据库

| 数据 | 大小 |
|---|---:|
| 迁移后的空库 | 10 MB |
| + 10,000 用户 + 2,001 题 | 15 MB |
| + 100,000 条提交 | **157 MB** |
| 其中 submissions 表 | 140 MB（堆 131 MB + 索引 9.6 MB） |
| WAL 目录（造数后） | 193 MB（受 `max_wal_size` 约束，默认上限约 1 GB） |

**增长约 1.4 KB/提交**（按 800 B 代码 + 10 个测试点结果估算）。实际代码最长 64 KiB，测试点多的题目结果 JSON 也更大，建议按 **2–5 KB/提交** 做容量规划：

- 10 万提交：约 0.2–0.5 GB
- 100 万提交：约 2–5 GB
- 1000 万提交：约 20–50 GB（超出 30 GB）

用户和题目本身很小：10,000 用户约 4 MB，2,000 题约 1.6 MB。

### 6.2 Redis

2,000 个登录会话时 Redis 约 2.9 MB（约 1.2 KB/会话）。排行榜缓存、队列和限流键都很小。测试中把 Redis `maxmemory` 设为 192 MB，余量很大。

### 6.3 Docker 镜像与系统

| 项目 | 大小 |
|---|---:|
| gcc:14 | 1.49 GB |
| golang:1.26 | 889 MB |
| eclipse-temurin:21-jdk | 502 MB |
| python:3.12-slim | 145 MB |
| postgres:17 | 477 MB |
| redis:7 | 136 MB |
| server + judge 镜像 | 约 224 MB |
| **镜像合计** | **约 3.87 GB** |
| Ubuntu 20.04 最小系统 + Docker | 约 3 GB |
| 前端 dist | 6.6 MB |
| 构建缓存（若在服务器构建） | 0–3 GB，可清理 |

基础占用约 **7–10 GB**，30 GB 盘剩余约 **18–21 GB** 给测试数据、上传文件、日志和备份。

### 6.4 30 GB 能放多少测试数据

按剩余 18 GB 计算：

| 每题测试数据 | 可放题数（约） |
|---:|---:|
| 20 MB | 900 题 |
| 50 MB | 360 题 |
| 100 MB | 180 题 |
| 200 MB（Hydro 单题上限） | 90 题 |

头像（≤2 MiB/张，通常几百 KB）和证书（≤5 MiB/张）也会占用一部分。1000 张证书按 1 MB 估算约 1 GB。

### 6.5 日志是最大的隐性风险

后端每个请求写一行日志，实测约 **100 B/行**：

- 100,000 次请求 → 约 10 MB
- 100 RPS 持续一天 → 约 **0.86 GB/天**
- 400 RPS 持续一天 → 约 **3.5 GB/天**

Docker 默认 `json-file` 日志驱动**不轮转**，长期运行可能把 30 GB 写满。必须在 `/etc/docker/daemon.json` 配置：

```json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
```

修改后 `systemctl restart docker`。Nginx 的访问日志同样要轮转或关闭。

## 7. 8 Mbps 带宽评估

8 Mbps 理论约 **1 MB/s**（实际 0.9 MB/s 左右）。

### 7.1 前端页面

| 页面 | gzip 传输（实测/构建产物） | 8 Mbps 下单用户耗时 |
|---|---:|---:|
| 首页 | 约 164 KB | 约 0.16–0.20 s |
| 题目详情（含 Markdown 异步 chunk） | 约 268 KB | 约 0.27–0.33 s |
| 提交页（含 CodeMirror chunk） | 约 283 KB | 约 0.28–0.35 s |

单个用户完全没问题。50 人同时冷加载题目详情约 13.4 MB，需要约 **13 秒**（每人分到 1/50 带宽）；但浏览器会缓存 `/assets/`，重复访问只加载 API 数据。

### 7.2 API

| 接口 | 平均响应 | 8 Mbps 理论上限 |
|---|---:|---:|
| 浏览混合请求 | 4.3 KB | 约 **230 RPS** |
| 提交记录列表 | 7.5 KB | 约 133 RPS |
| 比赛榜单（100 人） | 39.7 KB | 约 **25 RPS** |
| 登录 | 0.6 KB | 带宽可忽略 |
| 客观题提交 | 70 B | 带宽可忽略 |

- 浏览混合在 4 核上能跑约 400 RPS，但 8 Mbps 只能承载约 **230 RPS**。也就是说：**CPU 还有余量时，带宽会先到顶**。
- 比赛榜单 8 Mbps 约 25 RPS；前端 30 秒刷新一次，100 人在线只需 3.3 RPS，余量很大。
- 真正会打满 8 Mbps 的是：大量用户同时首次访问（冷缓存）、频繁手动刷新榜单、批量下载/上传。

### 7.3 大文件上传

- Hydro 题包 200 MB：8 Mbps 下约 **200 秒（3.3 分钟）**（假设上下行对称）。
- 测试点上传 40 MB：约 40 秒。
- 云服务器的“8 Mbps”通常指**出方向**，入方向可能更高；如果入方向也是 8 Mbps，导入大题包会比较慢，建议在本地导入后传数据库/存储，或临时升带宽。

### 7.4 带宽结论

**8 Mbps 对小型 OJ 够用**：正常刷题、看题、看榜、提交都不会卡；100 人比赛按 30 秒刷新榜单约 1.1 Mbps。需要注意的是冷加载和比赛高峰，建议开启 Nginx gzip + 静态资源长期缓存，并避免在比赛期间导入大题库。

## 8. 4C4G / 30GB / Ubuntu 20.04 综合评估

| 项目 | 评估 | 说明 |
|---|---|---|
| 4 核 CPU | ✅ 够用 | 浏览约 400 RPS；评测并发 1 时仍留 3 核给 API |
| 4 GB 内存 | ⚠️ 刚够 | 空闲约 0.8 GB；评测并发 1 峰值约 2.5 GB；并发 2 最坏会接近 4 GB |
| 30 GB 磁盘 | ⚠️ 够小规模 | 基础 7–10 GB，剩 18–21 GB；题库大或日志不轮转会很快满 |
| 8 Mbps | ✅ 够用 | 小型 OJ 和 100 人比赛足够；冷加载/大上传是短板 |
| Ubuntu 20.04 | ⚠️ 可用但建议升级 | 标准支持已于 2025-04 结束；Docker 官方已不把 20.04 列为受支持平台 |

### 8.1 Ubuntu 20.04 注意事项

- 内核 5.4、cgroup v1 可以运行本项目；PostgreSQL 17、Redis 7、静态 Go 二进制都没有问题。
- Ubuntu 20.04 已过标准支持期，安全更新需要 ESM；Docker 官方当前主要支持 22.04/24.04。**上线前建议升级到 Ubuntu 22.04 LTS 或 24.04 LTS**。
- 如果暂时不升级：
  - 用 Docker 官方 apt 源安装 Docker Engine + Compose 插件，不要用系统自带的 20.10。
  - 保持 ESM 安全更新。
  - 设置 `vm.overcommit_memory=1`（Redis 建议）。
  - 容器加 `TZ=Asia/Shanghai`，否则签到/活跃度的“本地自然日”会按 UTC 计算。
- Go 1.26、Node 22 只在构建时需要；运行时只需要 Docker 和静态文件，不需要在服务器装 Go/Node。

## 9. 推荐配置

| 场景 | CPU | 内存 | 磁盘 | 带宽 | 说明 |
|---|---:|---:|---:|---:|---|
| 演示/只做客观题/不跑代码评测 | 2 核 | 2 GB | 20 GB | 3–5 Mbps | judge 不启动或独立 |
| **小型 OJ（当前服务器）** | **4 核** | **4 GB** | **30–40 GB** | **8 Mbps** | judge 并发 1；控制题库体积 |
| 常规比赛（100–300 人） | 4 核 | **8 GB** | 60–80 GB | 20 Mbps | judge 并发 2 |
| 多校/大型部署 | 8 核+ | 16 GB+ | 200 GB+ | 50 Mbps+ | judge 独立机器/多实例 |

**你的服务器属于第二行**：能用，适合小型 OJ。最值得优先升级的是**内存到 8 GB**（换评测并发和比赛稳定性），其次是**磁盘到 60 GB**（如果题库测试数据多）。CPU 和 8 Mbps 对当前规模不是瓶颈。

## 10. 部署前必须做的配置

### 10.1 评测并发

```bash
KAPOJ_JUDGE_CONCURRENCY=1
```

4 GB 机器不要用默认的 2。8 GB 可以设 2。

### 10.2 Docker 日志轮转

`/etc/docker/daemon.json`：

```json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
```

然后 `systemctl restart docker`。否则高流量下日志可能每天增长数 GB。

### 10.3 时区

给 server / judge 容器加：

```bash
TZ=Asia/Shanghai
```

或在 compose 中挂载 `/etc/localtime:/etc/localtime:ro`。签到、活跃度按服务器本地自然日计算。

### 10.4 PostgreSQL 连接数

测试中 100 并发请求触发了 `max_connections=100` 耗尽，出现 36 个 500。建议：

- 在代码里给 GORM 设置连接池上限（例如 `MaxOpenConns=40`、`MaxIdleConns=20`），让请求排队而不是报错；
- 或把 PostgreSQL `max_connections` 提到 200，并用 PgBouncer；
- 小型部署至少避免瞬时 100+ 并发请求直接打到数据库。

### 10.5 Nginx 前端

- `gzip on`，`gzip_types` 覆盖 JS/CSS/JSON/SVG；
- `/assets/` 设置 `Cache-Control: public, max-age=31536000, immutable`；
- SPA 回退 `try_files $uri $uri/ /index.html`；
- 访问日志轮转或关闭。

### 10.6 备份

数据库和 `KAPOJ_STORAGE_DIR`（题目测试数据、checker、徽章、证书、头像）必须一起备份。30 GB 盘上不建议保留多份本地备份，备份应放对象存储或另一台机器。

### 10.7 磁盘清理

- 定期 `docker builder prune` 清理构建缓存（服务器上构建会占 2–3 GB）。
- 用 `docker system df` 查看镜像/容器/缓存占用。
- 监控 `df -h`、`pg_database_size`、`du -sh $KAPOJ_STORAGE_DIR` 和 Docker 日志目录。

## 11. 已知性能风险与优化建议

按优先级排序：

1. **提交记录列表的 COUNT 查询**：10 万提交时 14 RPS、P95 1.07 s。建议缓存总数、优化 JOIN，或在题库规模上来前处理。
2. **RBAC 实时权限查询**：每个登录请求 3 条 SQL，是浏览类 CPU 的主要来源。可加 5–30 秒短缓存（权限变更延迟几秒通常可接受），能显著提升并发。
3. **评测每测试点启动一个容器**：10 个测试点约 10 秒/份。可考虑把多个测试点合并到一次容器运行，或增加评测机。
4. **数据库连接池无上限**：高并发会耗尽 `max_connections`。设置池上限或 PgBouncer。
5. **Docker 日志不轮转**：磁盘隐性增长的最大来源，必须配置。
6. **Go 编译慢**：Go 首次编译约 7.6 秒/315 MB（每次容器都是冷缓存）。Go 提交多的话可考虑预热 GOCACHE 或单独镜像缓存。

## 12. 复现与上线前复测

本次测试的压测脚本和数据未提交到仓库（临时环境）。上线前建议在目标 Ubuntu 服务器上用真实数据复测以下四项：

```bash
# 1. 空闲资源
docker stats

# 2. 首页/题目/提交页首次加载
# 浏览器 DevTools → Network → Disable cache，记录 transfer size

# 3. 50 并发浏览 5 分钟
# 观察 docker stats 中 server/postgres 的 CPU，以及 P95 延迟

# 4. 提交 10 份 C++（10 个测试点）
# 记录从提交到 accepted 的时间、judge 并发 1/2 的差异
```

如果在目标服务器上 50 并发浏览时 PostgreSQL 长期接近 100% CPU，可以考虑：

- 把 PostgreSQL 的 `shared_buffers` 从 128 MB 提到 256–512 MB；
- 给 RBAC 加短缓存；
- 升级到 8 GB 内存并把更多核分给数据库。

---

**最终建议：** 当前 4C4G/30GB/8Mbps 可以作为小型 kapOJ 的生产环境。先按第 10 节完成 judge 并发 1、日志轮转、时区、Nginx 缓存和备份配置；如条件允许，把 Ubuntu 20.04 升级到 22.04/24.04。如果后续要做大规模比赛或导入大量测试数据，优先升级内存到 8 GB、磁盘到 60 GB 以上。
