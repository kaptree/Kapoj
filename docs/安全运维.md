# 安全运维与风险评估

> 本文件记录 kapOJ 部署面的安全边界、评测节点 Docker socket 加固方案与残余风险。与 [`数据备份与恢复.md`](数据备份与恢复.md) 同级维护。

## 1. 评测节点威胁模型

- judge 会消费用户提交，并在嵌套 Docker 容器中编译/运行不可信代码。沙盒负责限制用户程序；judge 进程本身属于**受信任控制面**。
- 直接挂载 `/var/run/docker.sock` 等价于把宿主机 Docker 控制面交给 judge 容器；一旦 judge 被逃逸或供应链漏洞攻破，攻击者可创建特权容器、挂载宿主目录或删除卷。
- 因此 judge 不应直接访问宿主 socket；默认通过白名单代理，并只在内部网络暴露。

## 2. 方案对比

| 方案 | 做法 | 优点 | 代价 / 风险 | 结论 |
|------|------|------|-------------|------|
| a. judge 独立节点 | judge + socket-proxy 部署在独立主机；server/web/DB/Redis/MinIO 留在主节点 | 隔离最强；评测爆炸半径与 Web 分离；可单独扩容 | 多一台主机与网络/监控/升级成本；需要共享 DB/Redis/MinIO 连通性 | 推荐中大型/公开站点采用；部署步骤见运行手册 §12 |
| b. socket-proxy 白名单 | judge 连 `tecnativa/docker-socket-proxy`，只代理容器生命周期与 exec | 改动小；阻断 system/volume/network/images/auth 等危险 API；无需改 judge 业务代码 | 代理仍在 Docker 控制面；`CONTAINERS=1` 仍允许容器级操作；代理自身被攻破仍有风险 | **默认落地** |
| c. rootless Docker | 以非 root 用户运行 dockerd，judge 通过其 socket/代理访问 | 去掉 root daemon，降低宿主级提权面 | 需要 cgroup v2 delegation、overlay/网络/端口配置；部分内核/发行版兼容性差；排障复杂 | 可选进阶，见运行手册 §12.5 |

## 3. 默认控制（b + a）

- `socket-proxy` 仅加入独立 `judge-socket` 内部网络，不映射宿主端口；server/web 默认网络不可达。
- 代理只读挂载宿主 socket，容器 `read_only`、`cap_drop: ALL`、`no-new-privileges`，并以 `tmpfs` 提供 `/tmp`、`/run`。
- judge 不挂载 `/var/run/docker.sock`，`DOCKER_HOST=tcp://socket-proxy:2375`。
- 白名单只开启：
  - `CONTAINERS=1`：create/start/stop/delete/list/inspect/logs/archive 等容器端点；
  - `EXEC=1`：`/exec/*`；
  - `POST=1`：允许上述端点使用 POST/DELETE；
  - `ALLOW_START/ALLOW_STOP/ALLOW_RESTARTS=1`：容器生命周期；
  - `PING/VERSION/INFO=1`：客户端与健康检查所需只读接口。
- 明确关闭：`SYSTEM`、`VOLUMES`、`NETWORKS`、`IMAGES`、`EVENTS`、`AUTH`、`SECRETS`、`SWARM`、`BUILD`、`PLUGINS`、`SERVICES`、`NODES`、`TASKS`、`CONFIGS`、`SESSION`、`DISTRIBUTION` 等。
- `docker system prune`、`docker volume ...`、`docker network ...`、`docker image ...` 应返回 403，可用于验收。

## 4. 残余风险

1. **代理不是针对“已完全控制的 judge”的强安全边界**：`CONTAINERS=1` + `POST=1` 允许任意容器 create（包括 `Privileged`、宿主 bind mount 等请求体参数），`EXEC=1` 也允许 exec 到同一 daemon 上的其他容器。socket-proxy 能阻断误用/常见破坏（prune、volume、network、image、auth），但不能替代独立节点、rootless 或更强的 gVisor/Kata/授权插件隔离。
2. `CONTAINERS=1` 不是“只允许 create/exec”的逐路径白名单：代理按容器 API 前缀放行，仍允许容器 inspect/list/delete 等。若需要更细粒度，应自建反向代理策略或在独立节点上进一步限制。
3. proxy 容器仍挂载宿主 Docker socket；宿主内核/Docker daemon 漏洞、恶意的容器镜像或代理镜像供应链问题仍可能突破。
4. socket-proxy 无 TLS/认证，安全性依赖 Docker 网络隔离；不得给 proxy 映射公网端口，也不要把 server/web 加入 `judge-socket`。
5. 直连回退 `KAPOJ_JUDGE_DOCKER_DIRECT=1` 会绕过代理，只应用于代理故障排查，完成后应立即恢复。
6. rootless Docker 不是默认配置；启用前需验证 cgroup、镜像、tmpfs、网络与评测镜像兼容性。

## 5. 运维检查

```bash
# 代理与 judge 是否健康
docker compose -f docker/docker-compose.yml -f docker/docker-compose.prod.yml --profile app ps socket-proxy judge

# 从 judge 容器内验证危险 API 被拒绝（应为 403）
docker compose -f docker/docker-compose.yml -f docker/docker-compose.prod.yml --profile app \
  exec -T judge sh -c 'DOCKER_HOST=tcp://socket-proxy:2375 docker system prune -f; true'
docker compose -f docker/docker-compose.yml -f docker/docker-compose.prod.yml --profile app \
  exec -T judge sh -c 'DOCKER_HOST=tcp://socket-proxy:2375 docker volume ls; true'

# 正常沙盒链路（宿主/CI）
cd apps/judge && KAPOJ_DOCKER_TESTS=1 go test -p 1 ./internal/sandbox/
```

## 6. 事件处置与回退

- 怀疑 proxy 被绕过或 judge 被攻破：立即停止 judge 与 proxy，保留容器/日志证据，轮换 `.env` 中数据库、MinIO、JWT 与 AI/邮件密钥，审计 `admin_audit_logs`、Docker 事件与网络访问。
- 临时回退直连：`sudo KAPOJ_JUDGE_DOCKER_DIRECT=1 bash deploy.sh update`；该模式仅用于恢复服务，恢复后必须切回代理。
- 独立评测节点故障：按运行手册 §12.4 在备用节点启动 judge + socket-proxy，确认 `KAPOJ_JUDGE_INSTANCE` 唯一，避免两个实例抢占同一队列任务。
